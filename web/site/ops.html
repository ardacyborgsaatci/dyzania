How Wrenbook runs

Five automations, one team each, one shared set of rules. This page says what is running today and what is not.

    How they hand work over

    1. Support to sales. A support email asking about pricing or a demo becomes an unscored lead. No reply is sent to the sender.
    2. Sales to booking. A hot lead gets a draft inviting them to book. A person reads and sends it.
    3. Voice to sales. A caller who asks for a demo is shown the sales form. The voice line never takes an email address.
    4. Finance to ops. A bill that needs review is logged, listed in the daily digest, and above a set amount alerts the owner.

    The handoff code is written and tested in the repository. It goes live together with the rebuilt n8n workflows, in one cutover.

    Rules every automation follows

    • Drafts only. No workflow sends mail to a customer. The only send nodes email the owner.
    • Email is data. Text from outside is wrapped and never treated as an instruction. Suspected injections get no draft and go to a person.
    • Code decides, models suggest. Model output is checked against a schema and re-validated. The booking agent can only pick from slots that code already checked.
    • Metadata only in logs. The shared event log holds short summaries with no email addresses.
    • One budget. All public demos share a daily limit so they cannot use up what the real inbox needs.

    Wrenbook is a fictional company made for a portfolio project. All people, companies and emails shown are invented. Nothing is ever sent to a customer automatically.
